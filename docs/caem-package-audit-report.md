- **BLOCKER** — will crash the run, produce wrong numbers, or corrupt outputs. Must fix before Vast launch.
- **MAJOR** — wrong behaviour in a meaningful edge case, inconsistency with thesis spec, silent data loss, or a latent bug waiting for the right input.
- **MINOR** — cosmetic, style, dead code, hardcoded magic number, missing docstring, weak logging. Safe to ship without, nice to fix.
- **NOTE** — design observation or question, not necessarily wrong. Discuss before acting.

- **SYN** — syntax, import, AST-level
- **LOG** — logic / correctness bug

- **TOD** — TODO/FIXME/XXX straggler

  **Evidence chain (all three sites confirmed by grep, not inferred):**
  1. `caem/verification/verifier.py:310` — `passage_retriever: Optional[Callable[[str, int], List[str]]] = None` (default None)
  2. `caem/verification/verifier.py:320` — `self.passage_retriever = passage_retriever` (only assignment; no post-init setter exists anywhere in the codebase)
  3. `caem/verification/verifier.py:674-675` — `if self.passage_retriever is None: return []` (silently yields empty passage list)
  4. `caem/pipeline.py:222-230` — the **ONLY** production construction site for `UnifiedVerifier(...)` — does **NOT** pass `passage_retriever=`
  5. `caem/pipeline.py:218-221` docstring claims *"Passage retrieval for grounding signals is threaded through the same PassageStore used by Tier 3 RAG"* — the docstring is a lie relative to the code beneath it
  6. `tests/test_verifier.py:201` also sets it to None, so tests have been green while shipping this bug

  **Consequence cascade (every downstream signal and decision path that dies):**

  - `_score_p_ground` (verifier.py:696-712) returns `(p_ground_max=0.5, p_ground_mean=0.5)` on empty passages
  - `_score_p_contra` (verifier.py:714-723) returns `p_contra=0.0` on empty passages
  - `_score_atomic` (verifier.py:725-761) returns `([], [], p_ground_mean=0.5)` on empty passages, so `p_ground_atomic` is fixed at 0.5
  - Four of the nine verifier signals are therefore **constant-valued** in production: `p_ground_max=0.5`, `p_ground_mean=0.5`, `p_ground_atomic=0.5`, `p_contra=0.0`
  - **Early-exit confabulation gate** (`u_internal ≥ 0.70 AND p_ground_max ≤ 0.20`) can NEVER fire — `p_ground_max` is locked at 0.5 which exceeds the 0.20 threshold. The gate Ch4 §"Early-exit confabulation detection" describes as a first-line defence against high-confidence hallucinations is non-functional.
  - **Contradiction hard veto** (`p_contra ≥ 0.30 → DISCARD` at verifier.py:805-813) can NEVER fire — `p_contra` is locked at 0.0. The veto Ch4 §"Contradiction veto" promises as an independent safety path never triggers.
  - **ABSTAIN decision class** (requires `u_stored < 0.45 AND p_ground_max < 0.20`) can NEVER fire — same `p_ground_max` lock. Every "don't know" case that should have routed to ABSTAIN is being silently forced into DISCARD or DEFERRED.
  - Composite `u_stored` reduces to a five-signal weighted average over `u_token`, `u_dropout`, `u_internal`, `s_avg`, `h_norm` plus three constants — the thesis's "nine-signal aggregation" claim becomes a five-signal aggregation plus three dummies.
  - Numerically: with the three grounding constants contributing a fixed offset of roughly `0.225` (assuming the 0.15+0.15+0.15 weights in the docstring line 40-47 sum to 0.45 × mean(0.5,0.5,0.5) = 0.225), the *achievable* `u_stored` range shrinks. Max u_stored from the five live signals ≈ 0.775. Still above the 0.65 STORE threshold, so storage still happens, but the ABSTAIN class becomes unreachable even on empty-output cases.

  **Signature mismatch discovered while auditing the fix path:**
  - Verifier expects `Callable[[str, int], List[str]]` — i.e. `fn(query_str, k) → list of passage strings`
  - `PassageStore.search` at `caem/retrieval/rag.py:193` has signature `def search(self, query_embedding: np.ndarray, k: int = 5) -> List[Tuple[str, float]]` — takes an **embedding** (not a string) and returns `(passage, score)` tuples (not bare strings)
  - Fix cannot be `passage_retriever=passage_store.search` — requires an adapter closure that encodes the query and strips the scores, e.g.
    ```python
    def _retriever(q: str, k: int) -> list[str]:
        emb = encoder.encode(q)
        return [p for p, _ in passage_store.search(emb, k=k)]
    ```

  **Thesis divergence this creates:**
  - Ch1 Claim A1 ("nine-signal verifier") becomes empirically false in production — only five signals carry information
  - Ch4 §"Grounding signals" describes `p_ground_max`, `p_ground_mean`, `p_ground_atomic`, `p_contra` as independent checks; in production they are all dummies
  - Ch4 §"Early-exit confabulation detection" and §"Contradiction veto" describe mechanisms that **cannot fire** on the code as shipped
  - Ch5 Table 5.X (mechanism evidence table, `print_mechanism_table`) reports hallucination reduction; any "reduction" measured with the current verifier is driven by the five live signals only, and the contribution of grounding to hallucination reduction is silently zero — which conflates "grounding works" with "five-signal aggregation works"

  **Remediation path (flag only, not a fix):**
  1. In `caem/pipeline.py:222-230`, before `UnifiedVerifier(...)`, build the adapter closure shown above using the same `passage_store` and `encoder` already constructed in `CAEMPipeline.__init__`
  2. Pass `passage_retriever=<adapter>` to the `UnifiedVerifier` constructor
  3. Unit-test path: add a test that constructs a pipeline with a populated PassageStore and asserts `p_ground_max` varies across queries (currently it is identically 0.5)
  4. Ch1/Ch4 rewrite: once wired, the nine-signal claim becomes true again and Table 5.X is meaningful. Until wired, the claim should be hedged or the code must ship this fix.

  **Severity: BLOCKER, not MAJOR.** The thesis's central verification contribution — the nine-signal aggregation with grounding + contradiction veto + ABSTAIN class — is silently non-functional in production. Every experimental result gathered with this code understates (or misreports) the role of grounding. Must be fixed before any Vast AI main experiment launch (Task #74) or the mechanism evidence table (Ch5) will be measuring the wrong system.

  **RESOLUTION (Task #112 + Task #123 + Task #127, Wave 1 bundle):**

Therefore `getattr(post_conf, "u_token", None) if post_conf else None` short-circuits to `None` every call, the verifier recomputes the signals, and the claimed optimisation never fires. Either the optimisation was a partial refactor (compute `post_conf` in `_tier2`, plumb through) or the code is defensive for a future change. As-is, the comment lies about performance and the two `getattr` calls are dead. Check `UnifiedVerifier.verify` to confirm whether it actually reuses `u_token`/`u_dropout` when passed.

- **MAJOR-P2 (pipeline.py:701, LOG/QUA) — private API call `_should_prune()` across module boundaries.** `if self.memory_store._should_prune()` at line 701 and `self.memory_store.prune()` at line 703. `_should_prune` is defined at `memory/store.py:480` with a leading underscore (private). MAJORs Wave 1 (Task #90) cleaned up private-API calls across the scripts layer but missed this one inside `caem/pipeline.py`. Either promote `_should_prune` → `should_prune` (public) or wrap it in a public method on `EpisodicMemoryStore.add()` so the pipeline doesn't have to orchestrate pruning at all.

- **MAJOR-P3 (pipeline.py:758, CON) — Tier 1 "accepted" uses `retroverify_prune_threshold` not `store_threshold`.** `accepted = entry.u_stored >= self.config.retroverify_prune_threshold` mirrors the same threshold-constant mix-up that NOTE 30 caught in `run_purity_validation.py`. The entry being read was originally admitted under the Stage 5 STORE gate (which uses `store_threshold`), but its Tier-1 retrieval "acceptance" for `retrieval_count` / `success_rate` accounting is being measured against the cycle-boundary pruning gate. These two thresholds are set independently in `CAEMConfig` and can diverge. Thesis §"Stage 7 storage" / §"Retroactive re-verification" distinguishes them; Ch5's retrieval-quality analysis (if/when it reports success_rate per Tier 1) needs to know which threshold is being applied. Check thesis §Tier-1 retrieval statistics / Table 5.X for the canonical threshold and align the code.

- **MAJOR-P4 (pipeline.py:454, CON/LOG) — Tier 2→3 escalation silently keeps `routing.tier == 2` in `PipelineResult`.** When Tier 2 generation fails or returns empty, `_tier2` escalates via `return self._tier3(query), None, True` (line 454 / 458). The parent `answer()` method at line 329 entered this branch with `routing.tier == 2`, calls `_tier2`, receives the escalated answer, but never updates `routing.tier` to 3 before passing into `_maybe_store` / the returned `PipelineResult`. Consequence: (a) Table 5.X tier-distribution histograms under-report Tier 3 usage by exactly the escalation rate; (b) `pipeline.answer().tier` is a lie for escalated calls. The `escalated` field is set on `PipelineResult` but downstream aggregation (e.g. `run_all(...)` tier_frac computation) reads `result.tier`, not `result.escalated`. Two-way fix needed: update the effective tier on escalation AND decide whether escalated calls count in tier_2_frac or tier_3_frac for Ch5 reporting. Thesis §Table 5.X routing distribution does not currently specify which bucket escalations fall into.

### `caem/memory/deferred.py`

- **MAJOR-D1 (deferred.py:93-123 + 168-234 + 355-358, LOG/CON) — `DeferredEntry` has NO `reasoning_chain` field; on promotion, `reasoning_chain = de.answer` silently substitutes a bare answer string for the full chain-of-thought, degrading up to ~20% of the training pool.**

  **Evidence chain (three sites, all confirmed by reading the full file):**
  1. `deferred.py:93-123` — `DeferredEntry` dataclass has fields `question`, `answer`, `embedding`, `storage_cycle_pushed`, `initial_u_stored`, `initial_decision`, `age`, `source_benchmark` — **no `reasoning_chain`** and no placeholder for it.
  2. `deferred.py:168-234` — `push(question, answer, embedding, storage_cycle, vout, source_benchmark)` signature does not accept a reasoning_chain parameter; the only textual fields captured are `question` and `answer`.
  3. `deferred.py:355-358` — on promotion, the code constructs `EpisodicEntry(question=de.question, reasoning_chain=de.answer, answer=de.answer, ...)` — assigning the answer string to the `reasoning_chain` field.

  **Consequence cascade:**
  - `EpisodicEntry.reasoning_chain` is the field Ch4 §4.3 defines as *"the core transferable knowledge"* — it is the chain-of-thought that the SelfImprovementLoop fine-tunes on (`self_improvement.py` `_collect_episodes` builds the training dataset from `entry.reasoning_chain`).
  - For the STORE path, `pipeline._maybe_store` captures the full CoT from Tier 2 generation and stores it into `reasoning_chain` (pipeline.py constructs `EpisodicEntry(reasoning_chain=reasoning, answer=answer, ...)` with separate fields).
  - For the deferred-promotion path, `de.answer` is a short answer string (3-20 tokens typical for Flan-T5 on QA benchmarks); fine-tuning on `reasoning_chain = "Paris"` instead of `reasoning_chain = "The capital of France is Paris because..."` loses the transferable reasoning signal the thesis claims is the mechanism behind self-improvement.
  - Quantitative impact: Ch4 §4.9 states DEFERRED entries are held at `0.45 ≤ u_stored < 0.65` pending cycle-boundary reconsideration. In a 10-cycle run with a "healthy trajectory" (Ch4 §4.7 closing paragraph) where mass shifts from DEFERRED into STORE cycle-over-cycle, a non-trivial fraction of the final training pool originates from deferred promotions. If that fraction is 10-30%, then 10-30% of the training data has `reasoning_chain` collapsed to the answer string — silently weakening the very signal Ch4 Claim A3 (self-improvement from verified triples) depends on.

  **Thesis divergence:**
  - Ch4 §4.9 describes deferred reconsideration but does **not** specify that reasoning_chain is preserved across the push→promote boundary. The thesis assumes — but does not state — that a promoted DEFERRED entry is semantically identical to a STORE-path entry.
  - Ch4 §4.3 requires `reasoning_chain` to be the full CoT; the deferred path violates this.

  **Remediation path (flag only, not a fix):**
  1. Add `reasoning_chain: str` field to `DeferredEntry` (line 93-123).
  2. Add `reasoning_chain: str` parameter to `push()` (line 168).
  3. Update the sole call-site in `pipeline._maybe_store` to pass `reasoning_chain=reasoning` alongside `answer=answer`.
  4. On promotion (line 357), replace `reasoning_chain=de.answer` with `reasoning_chain=de.reasoning_chain`.
  5. **Migration concern:** any saved deferred-buffer pickles from prior runs (Task #81 resume path) will unpickle as `DeferredEntry` instances missing the new field. Either set a default (`reasoning_chain: str = ""`) to accept legacy payloads, or bump `save_version` and refuse to load old buffers on a schema mismatch. The `""` default has the side-effect that legacy entries promoted post-migration will still have empty reasoning_chains, but it's non-fatal.

  **Severity: MAJOR, not BLOCKER.** Production does not crash — the field assignment is silently wrong, not structurally broken. But for a thesis whose central contribution is *self-improvement via verified reasoning traces*, training on answer strings instead of reasoning chains is directly counter-thesis. Fix before Vast main run (Task #74) if the deferred-promotion pathway is expected to contribute to training data; lower-priority if the expected DEFERRED→STORE rate is near zero in the 10-cycle regime (Ch5 pilot numbers would tell).

### `caem/verification/verifier.py`

- **MAJOR-V1 (verifier.py:272-276, LOG/EDG) — `_parse_atomic_facts` preamble heuristic is too weak; preamble contaminates `per_atom_entail` and pulls `p_ground_atomic` down on most Flan-T5 outputs.** The preamble filter at lines 272-276 only strips lines that `endswith(":")`. Flan-T5-Large routinely emits preamble without a colon (`"Here are the facts"`, `"Based on the passage"`, `"The answer is"`, `"To answer this question"`, `"Let me think"`). These lines leak into the atomic fact list, get sent to the NLI scorer as claims, and score ENTAILMENT probability near neutral (0.3-0.5) against any passage — dragging `p_ground_atomic` downward by a roughly constant offset per generated answer. Effect on the pipeline: even if grounding were wired (see BLOCKER-V1), `p_ground_atomic` would systematically under-report grounding quality because ~20-30% of "atomic facts" are actually meta-commentary. Suggested tighter heuristic: also strip lines starting with common preamble tokens (`Here`, `Based`, `To answer`, `Let`, `The answer is`, `In summary`) and lines ending with `?` (questions, not claims). Alternative: run a one-shot classifier ("is this a factual claim?") over each line — heavier but robust. Consequence for Ch5: any atomic-grounding numbers reported are noise-dominated by preamble contamination.

### `caem/confidence/pre_routing.py`

- **MAJOR-PR1 (pre_routing.py:249, DOC) — wrong encoder-layer count for Flan-T5-Large.** Comment at line 249 says *"Number of encoder layers (12 for Flan-T5-Large)"*. Flan-T5-Large inherits from `t5-large`, which has **24 encoder layers** (and 24 decoder layers), not 12. The *variance-ratio formula itself does not depend on this literal* (the code computes `L = len(hidden_states) - 1` from the actual tensor), but any reader (Aksan, committee, or a future contributor) who trusts the comment will reason about the wrong architecture. Also affects a reader's interpretation of what the ratio *means*: variance over 12 layers vs 24 layers has different statistical properties. Classified MAJOR-DOC because it is a factual error in a mechanism-critical comment, not a style issue.

### `caem/training/self_improvement.py`

- **MAJOR-SI1 (self_improvement.py:954-1003, QUA/DOC) — `_forgetting_score` is deprecated but lives alongside the active guard.** The method is tagged `DEPRECATED` in its docstring (lines 955-968) and explicitly not called by `run_cycle`, but it remains a ~50-line method in the class, complete with its own hardcoded magic number (`MAX_FORGETTING_EVAL_PAIRS = 50` at line 977). Risk: in a partial refactor, a call site for the deprecated method gets reintroduced (e.g. from an old unit test, or from `run_cyclic_ablation.py` which may have stale expectations), and the forgetting guard silently reverts to the TriviaQA-style probe that's known to be insensitive to catastrophic forgetting. Either (a) delete `_forgetting_score` entirely, or (b) convert it to `raise DeprecationWarning`-on-call with a clear message pointing to `measure_mmlu`.

- **MAJOR-SI2 (self_improvement.py:572, EDG/RES) — `torch.load(weights_path, map_location=self.device)` uses default `weights_only=False` (PyTorch ≥2.4 security warning).** PyTorch 2.4+ emits a `FutureWarning` when `weights_only` is unspecified because the default (False) unpickles arbitrary Python objects, opening an RCE surface if checkpoints come from untrusted sources. For research checkpoints this is tolerable, but (a) it floods the log with warnings every resume, obscuring genuine issues, and (b) a production-quality artefact should explicitly opt into the unsafe mode with justification, OR switch to `weights_only=True` (which only unpickles tensor state_dicts — perfect for model weights). ### `eval/metrics.py`

- **MINOR-M5 (metrics.py:485-495, RES) — `bootstrap_ci` Python-loop resampling is slow for 20k samples.** `n_bootstrap=1000` × `n=20000` = 2×10^7 `rng.choice` calls, ~10-30 seconds per call. - **MINOR-M6 (metrics.py:720-723, RES) — Mann-Whitney AUROC fallback is O(|pos|×|neg|), catastrophic at 20k samples.** The nested loop at 717-722 does pairwise comparisons; for 10k positives × 10k negatives = 10^8 operations, minutes-long. sklearn's `roc_auc_score` is O(n log n) via rank-sum. The fallback is triggered only when sklearn is missing (unlikely on Vast; sklearn is a hard dep), but if it IS triggered, reporting silently wedges for minutes. - **MINOR-M8 (metrics.py:544, CON/DOC) — McNemar continuity correction `(|n01-n10|-1)**2` is applied unconditionally; literature (Edwards 1948) prescribes it only when `|n01-n10| >= 1`.** For `n01 == n10` (equal disagreements, extremely improbable at n=20k but possible at n~50), the correction yields `(-1)**2 = 1` — a positive contribution where the uncorrected test would yield 0.
